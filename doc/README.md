# Requel documentation

This folder holds two very different kinds of writing, and telling them apart is the
whole point of the layout.

**Standing reference** describes how Requel works now. It is meant to still be true in
six months, and when the code changes underneath it, it gets updated. It lives in
`architecture/`, `guides/` and `ui/`.

**Work artifacts** are the paper trail of a single ticket — the plan written before the
work, the review written against a named commit, the rollup that tracked an epic. They
are correct *as of when they were written* and are never retro-edited. A plan that says
Spring Boot 3.3.4 is not stale; it is a record of what was true that week. These live in
`work/<release>/`, and each release starts with an empty folder.

If you are reading to find out how something works, read the first kind. If you are
reading to find out *why* something is the way it is, read the second.

## Where things go

| Folder | What belongs there |
|---|---|
| `architecture/` | How the system is built: authorization, module boundaries, the annotation registry, the import/unmarshalling strategy, the user/stakeholder model, dictionary loading. |
| `guides/` | How to run and operate it: releases, Docker, Maven toolchains, connecting an MCP client, AI assistant setup, the agent runbook. |
| `ui/` | The Angular layer as a system: design guide, shared components, bundle posture, zoneless readiness. |
| `work/<release>/` | Everything tied to a ticket in that release — `<issue>-<slug>-plan.md`, reviews, rollups, issue drafts. `<release>` is the reactor version's major.minor from the root `pom.xml`. |
| `work/backlog/` | Proposals and epics not yet scheduled to a release. When one gets an issue, it moves into that release's folder. |
| `archive/` | Superseded records of completed work that predates this scheme, and `2009-thesis/` for the original Harvard ALM thesis material. |
| `images/`, `samples/` | Assets. Shared by both kinds of document; they do not move. |

## Adding a document

Ask one question: **is this going to be true in six months, or is it a record of one
ticket?**

A record of one ticket goes in `work/<release>/`, named `<issue>-<slug>-plan.md` or
`<issue>-<slug>-review.md`. Nothing new belongs at the root of `doc/` except this file.

If a work artifact turns out to describe how the system actually works — it keeps getting
read, it keeps getting updated — that is the signal to promote it: move it into
`architecture/`, `guides/` or `ui/` and let its ticket history stay behind in git.

## The index

`work/<release>/INDEX.md` is generated by `scripts/gen-doc-index.sh`. It joins the issue
number in each filename against live GitHub state, so open/closed is never duplicated into
the files themselves — the issue is the source of truth and the index reads it fresh.

Run it after closing issues:

```bash
./scripts/gen-doc-index.sh          # current release, from pom.xml
./scripts/gen-doc-index.sh 2.1      # a specific release
```

Generating the index also runs `scripts/check-doc-links.sh`, which resolves every markdown
link under `doc/` and in the three root documents and fails on a broken one. It needs no
GitHub access and can be run on its own:

```bash
./scripts/check-doc-links.sh
```

Paths mentioned in prose rather than linked are reported separately and never fail the run —
an instruction, a conditional or a reference to another branch is not a defect, and a work
artifact is never retro-edited to make its old prose resolve. Ones that are known and
intended are recorded, with a reason, in `scripts/doc-link-allow.tsv`.
