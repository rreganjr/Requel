# Ticket #147 (5.6) — Bundle & dependency posture — implementation plan

Low-priority, ~1 day. Measurement, guardrails, and docs — no runtime/behavior
changes.

## Current state (survey)
- **Budgets already exist** in `angular.json` (production): initial
  `maximumWarning: 1MB` / `maximumError: 2MB`, anyComponentStyle `4kB`/`8kB`.
- **CI already enforces them.** `mvn verify` → frontend-maven-plugin runs
  `npm run build` → `ng build` (production by default), so a bundle over the
  2MB error budget fails the build; a warning prints in the log.
- **PrimeNG imports are already tree-shakeable** — every import is a
  per-component entrypoint (`primeng/button`, `primeng/table`, …); there is
  **no** bare `from 'primeng'` barrel import anywhere. So AC3 is satisfied
  today; the work is to *guard* it going forward.
- No bundle-stats script and no ESLint setup exist yet.
- Builder is `@angular/build:application` (esbuild); `ng build --stats-json` is
  supported and emits `stats.json` (analyze at https://esbuild.github.io/analyze/).

## AC-by-AC plan

### AC1 — documented bundle-stats command
- Add npm script: `"build:stats": "ng build --stats-json"` (emits
  `dist/requel-angular/stats.json`).
- Document in the new doc: run `npm run build:stats`, then drop `stats.json`
  into https://esbuild.github.io/analyze/ (or inspect the printed per-chunk size
  table, which the Angular build already prints).

### AC2 — budget warnings/errors called out
- No config change needed (budgets already enforced by the CI `ng build`).
- Document the budgets, the exact enforcement path (`mvn verify` → `ng build`),
  and how to read a warning vs a hard failure, in the new doc under a
  "Release gate" heading.

### AC3 — keep PrimeNG imports tree-shakeable (ESLint guard — Ron's call)
- Stand up a **minimal** flat ESLint config (`eslint.config.js`) for the app,
  deliberately scoped to a single rule so it passes clean on the current code
  and does not turn into a mass-lint cleanup:
  - `@typescript-eslint/no-restricted-imports` banning the bare `'primeng'`
    barrel with a message pointing at the per-component entrypoint. Per-component
    (`primeng/button`) and per-module (`primeng/api`) imports stay allowed.
- devDependencies (pinned, ESLint 9 flat config, Angular 21 compatible):
  `eslint`, `typescript-eslint`, `@eslint/js`, `angular-eslint`.
- Add `"lint": "eslint \"src/**/*.ts\""` script (plain eslint invocation — avoids
  adding an `ng lint` architect target to `angular.json`; keeps the change small).
- Wire a **lint step into `ci.yml`** next to the existing host-Node Vitest step
  so the guard runs in CI (frontend-maven only does `ng build`, not lint).
- Ruleset intentionally starts at just this guard; the doc notes it can grow later.

### AC4 — bundle-growth findings become follow-ups
- Run `npm run build:stats` once, record the **baseline** production initial +
  largest lazy chunk sizes in the doc.
- If the initial bundle is at/over the 1MB warning (or any chunk looks
  surprising), prepare a `gh issue create` command for a follow-up with a
  concrete size target (handed to Ron to run — no auto-filed issues). If nothing
  is over budget, the doc records the baseline and states no follow-up is needed.

## Deliverables
- `requel-angular/package.json` — `build:stats` + `lint` scripts; the four
  ESLint devDependencies.
- `requel-angular/package-lock.json` — regenerated by `npm install`.
- `requel-angular/eslint.config.js` — new, minimal flat config with the import guard.
- `.github/workflows/ci.yml` — a lint step.
- `doc/BUNDLE_AND_DEPENDENCIES.md` — the stats command, budgets & release gate,
  the PrimeNG import convention + guard, the recorded baseline, and the
  findings→follow-up process.
- `doc/147-bundle-dependency-posture-plan.md` — this plan.

## Verification gate
```
cd requel-angular
npm install                       # lock the new devDeps
npm run lint                      # passes clean (no barrel imports today)
npm run build:stats               # production build succeeds within budgets; emits stats.json
CI=1 npm test -- --watch=false    # unit suite unaffected (sanity; no src changes)
```
Add a deliberately-bad `from 'primeng'` import in a scratch file to confirm
`npm run lint` fails on it, then remove it (guard-works check).

## Out of scope
- No component/runtime changes; no dependency upgrades or removals.
- No broad ESLint ruleset — only the import guard (a full lint adoption is its
  own ticket, notable as a possible AC4 follow-up).
- Not enabling zoneless, not changing budgets' thresholds.

## Risks
- **ESLint flat config + Angular 21 version matrix.** Pin versions that match
  ESLint 9 / typescript-eslint 8 / angular-eslint 19–20; `npm install` + a green
  `npm run lint` is the check.
- **Lint avalanche** if the config pulls in recommended sets — avoided by scoping
  to the single rule.
- `package-lock.json` churn from the new devDeps — expected; it is part of the diff.
